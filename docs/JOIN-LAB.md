# Router join assessment and synthetic lab path

This module describes joining **one compatible border router** to a selected existing Thread network. It does not change the dataset of a whole network or commission a Matter accessory. Moving an accessory to another Thread network and adding a Matter fabric are separate operations. Automatic accessory transfer is optional for the first release.

`app/lib/join/` is a portable, pure Dart decision layer. It consumes evidence supplied by a future authorized device adapter; it has no network access or credential storage. The command runner in `app/tool/lab_join_harness.dart` has only an injected `SyntheticActuator`. It cannot dispatch a real device command, Petition, or dataset SET. Run its example with synthetic data only. No UI or API route enables joining.

## Assessment gate

A lab candidate needs a specific router model and firmware with a checked join-command capability; the owner-authorized device command and target dataset; a ready Thread state; a fresh authenticated target-network read matching the imported identity; and empty pending state. An existing source also needs a fresh authenticated read bound to the selected router. A new/uncommissioned source needs vendor attestation. The operator explicitly attests that the controlled source has no attached accessories; absent advertisements or an empty observed child table do not establish that. Unknown capability, authority, inventory, identity, source state or read status stops the plan. A router already verified on the target returns `alreadyJoined` without a command, even if join-command support, migration authority or empty-source attestation is absent. A pending update is still reported as a warning.

The assessment carries opaque in-memory identities for exact comparison; callers must derive them from authenticated network name, Extended PAN ID and channel evidence, never from a displayed name alone. Confirmation captures an in-memory copy of the selected source router, source identity if known, target router and identity, model, firmware, capability, readiness, inventory attestation and authority flags. Dispatch rejects a candidate whose reviewed fields changed; new evidence still has to pass assessment at send time. The redacted operation record exposes only a random operation ID, state and send time for a future persistence layer. It contains no dataset, PSKc, key, endpoint, router identity, model or network identity. A restart loses the in-memory confirmation and requires a new review. A future real adapter must choose its device by its own authorized handle and revalidate all evidence immediately before dispatch. Google documents `ThreadNetworkManagement.joinNetwork` on Android and iOS, but model and firmware support must be measured. Existing pinned OpenThread Commissioner `probe` is a read-only authenticated verifier; its Active/Pending dataset SET methods would operate on the network and are not a per-router join implementation.

## Operation and verification

The state path is `planned → confirmed → dispatching → observing → complete/needsAttention`. A dispatch intent must be durably recorded before any future real device command. A timeout or crash during dispatch is ambiguous: the restored operation becomes `needsAttention`, and it is never sent again automatically. Restart also invalidates a confirmation that had not yet dispatched, requiring a fresh review and confirmation. The synthetic harness reserves both the operation ID and source router synchronously before awaiting its actuator, so a second ID cannot dispatch the same source while the first command is pending or uncertain. The source lease remains held after uncertainty or failed observation. A later distinct join is admitted only after the first completes and fresh, post-dispatch source and target reads support a separately reviewed move. This in-memory lease is lab behavior; a real adapter needs durable cross-restart coordination. Cancel before dispatch is distinct from stopping observation after acceptance. A command response only begins observation.

Completion requires fresh authenticated reads after dispatch from the **same selected router** and the target network, both matching the authorized target identity with no pending update. The current harness admits only the attested-empty source. The verification model also accepts an exact affected-accessory list with one fresh operational read per subject after dispatch, for a future separately authorized migration route; a status flag alone cannot prove this. Interim old identity, pending update, missing reads or unknown accessory evidence remain `observing` while the defined observation period is open; a changed router binding is rejected immediately. At the end of observation, unresolved or failed evidence yields `needsAttention`. No universal observation duration is inferred.

The harness owns the authoritative operation after dispatch. Its
`stopObservation` method records the stopped state before queued verification
callbacks can run; a caller-supplied stopped reducer value is also preserved.
Older callback snapshots cannot revive observation or release the source lease.

## Hardware gate for a future adapter

Use an isolated router and a known target network with owner-authorized credentials, documented device command support and a model/firmware capability result. Establish the actual source inventory and a recovery method before any device command. The lab must observe command acceptance separately from router attachment, target reads and accessory operational reads. Test a missed response, lost connection, app restart and failed recovery. Rejoining the old network might be possible only if the device offers that command and old credentials remain usable; it is not a guaranteed rollback. No household router, vendor account or working accessory is an implicit test target.
